# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **The CI validation checks the workflows and the lessons of past CI failures against a baseline:** `tools/workflow_hygiene.py` and `tools/lessons_lint.py` (copies of the shared tools) run in the validation, and only findings that are not in `tools/workflow_hygiene_baseline.json` and `tools/lessons_lint_baseline.json` fail it, so what exists today stays as it is and a new one is caught. `python tools/workflow_hygiene.py --root . --detail` and `python tools/lessons_lint.py --repo .` list the findings.
- **The validation of the CI is the reusable one of the documentation hub:** the job `validate` calls `validate.yml` of EH3D-DOCS (pinned by commit) and what the repository checks besides it is in jobs of their own, with the check of the CHANGELOG.

## [0.1.0] - Shared core of both screens, rollback of a new image and server health check

- **The settings file is tested damaged:** `test_hmi` reads the settings file cut at every place and in 600 copies with bytes changed, inserted or cut (a fixed seed), and no value ever leaves its range. The counts of the host tests in the README are the ones of the CI.

- **A pull request must bring a line in the changelog when it changes the code:** `tools/changelog_pr_check.py` runs in the CI of every pull request (a label `no-changelog` skips it).

- **The two screens share one `core/`:** the settings (`hmi_config.hpp`, with the panel that moves the machine by hand and the kind of machine), the gate, the keyboard, the texts, the 37 languages (`locales/`), `machine.hpp` and the fonts with their code ranges are the same files in both, kept equal by the firmware base of EH3D-COMMON; what one screen does not use the other leaves alone. The fonts are built from the literals of both screens, in GitHub Actions, with `lv_font_conv` 1.5.3 and the fonts of LVGL 9.3.0 (`EH3D_EXTRA_LITERALS` in `tools/make_locales.py` names the other screen's file).
- **The screen says when the server answers but is not well:** the health check tells `degraded` and the note `ui.SrvDegraded` is shown, in the 37 languages.

- **The build in GitHub Actions lists the biggest stack frames:** with `EH3D_STACK_REPORT=1` (set only by that build) the compiler writes the stack use of every function and the build prints the twenty biggest of `main/` and `core/` in its summary, with a warning on any above 2048 bytes; the image does not change.

- **The orders of the screen are an enum:** every button sends an `Op` (`core/ops.hpp`: stop, start job, pause, resume job, tool changed, home, spindle on) in the action, and the application compares that and not the text of the order; the text stays as the id the confirmation shows and `op_of` reads it back, with a test through the whole table so that the two cannot drift.

- **A new image goes back when the screen does not run:** `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` is on and `main/image_confirm.hpp` confirms an image written by an update after 30 seconds of running, or sends it back to the previous one at once when the display does not start; an image flashed through the cable is not touched.
- **The first request to the server is its health check:** after a start or when the link was lost the screen asks `GET /api/v1/health` (open to anyone, no token goes with it) and tells "nobody answers" from "something answers that is not an EH3D server" (`classify_health` in `core/server_link.hpp`) before it asks for the fleet.
- **The host tests also run under AddressSanitizer and UBSan in the CI:** the same programs are built with `-fsanitize=address,undefined` and run (an undefined behaviour stops the test), and `test.sh` / `test.bat` run the same steps as the CI (the repository checks, the tests of the tools, the pictures and the languages, and the host tests).

## [0.0.9] - The touch screen follows the changer chaining, the positions of the tools, the jog panel and the stage notices of the job

- **The card of the work in hand:** under the lines of the machine page, four blocks as in the desktop program: the tool and its step (number, diameter, place in the bar, hole or cut X of N), the times (left, elapsed and the local hour the job is expected to end at), the position and the depth (X, Y, Z, the stroke, the feed and the turns of the spindle) and the counters (holes done or length routed, tool changes). What the server does not report is a dash, never an invented number; the hour comes from the system clock, or from `time_s` of the fleet, and `clock_utc_offset_min`.
- **The end of the drilling is a stage, not the end of the job:** when a drilling program ends and a routing program comes next, the screen plays its own notice (`stage.wav` of the voice chosen with `sound_stage`, or a tone) and shows a window saying that the routing comes next, with the buttons to follow it or to stop (switch `stage_window`). The sound of the end and the order to take the board out now wait until the server says the whole job was done; before, the end of the drilling played the sound of the end of the job.
- **A panel to move the machine by hand:** a cross for X and Y, Z, steps of 0.01, 0.1, 1, 10 and 50 mm, a continuous mode in which a held arrow goes in stretches, three speeds and four places kept. Nothing moves while a job runs (`jog_block_running`) or the hardware stop is on, the head stays inside the table (`jog_limits`) and goes up to the clearance over the board before it crosses it (`jog_safe_z`). The steps, the speeds, the clearance and the depth of the board are in `hmi.cfg`. A move by hand does not need a running job to be armed, and the gate refuses it with its own reason while one runs. The moves wait for the link to the node: until it exists the screen says that nothing was sent and keeps its position.
- **The bar of the tool changer:** on a machine whose model says ATC the job page shows a square per tool with its place and its state, and a window "Positions in the bar" with a drop-down list of places for every tool. A tool without a place, a place the machine does not define (`rack_places`) or two tools in one place stop the start and the screen says which tool and why (switch `rack_check`). The places are given in order, the small drills first and then the cutters, until the operator changes them.
- **Drilling and routing chained in one tool change:** the request of the job carries `request_version` 2 and a `rack` with `first`, `carry_in`, `carry_out`, `slots` and `carry_slot` (switch `rack_chain`); the drilling leaves its last tool in the chuck and the routing takes it over. A server that answers 400 or 422 gets the job again without the bar, and one that does not say `rack_applied` is believed: the screen shows in red that the tool changes were not chained and does not send the next program as a chained one. See `docs/SERVER_CONTRACT_NEEDS.md`.
- **The fleet is read more fully:** `time_s` of the answer and, for the running job, `position`, `feed`, `spindle_rpm`, `depth_mm`, `tool_changes`, `elapsed_s`, `routed_mm` and `tool_slot`, all optional.
- **Texts:** sixteen new texts in the 37 languages (the card, the stages, the panel by hand, the bar of the tool changer and the reason for a move refused while a job runs) and the fonts built again for the characters they need.
- **Settings:** `jog_steps`, `jog_step`, `jog_continuous`, `jog_speed_slow`, `jog_speed_medium`, `jog_speed_fast`, `jog_speed`, `jog_chunk_mm`, `jog_clearance_mm`, `jog_board_z_mm`, `jog_below_board_mm`, `jog_block_running`, `jog_limits`, `jog_safe_z`, `rack_places`, `rack_check`, `rack_chain`, `stage_window`, `clock_utc_offset_min` and `sound_stage`, with their keyboards in the list of the settings that the screen edits and their rules in `tools/selftest.py`. Every safety switch starts in its conservative position.
- **What the screen shares with the desktop program is written down:** `docs/PARITY_BUNGARD_GUI.md` lists each function, whether it is done, missing, not applicable or done in another way, and why.
- **Tests:** a ninth program, `test_parity` (227 checks), on the places of the bar and their validation, the chaining of the drilling and the routing and the request of the second version, the workflow on a machine with the tool changer (the retry without the bar, the reply of the server), the card of the work and its hour, the stages, the panel by hand (steps, limits, safe height, hold, places, blocks) and the new settings; `test_locales` follows the new keys.
- **Brand:** Add the application icon and the logos of the program.
- **Shared checks updated:** the validator also compares the badge and the Version row of the README with the manifest, fails when one of its checks cannot run, and the CHANGELOG step of the workflow reads the base branch from the environment.
- **A watchdog for the manual build:** `.github/workflows/build-watchdog.yml` looks every hour for a build that stays queued or running longer than the limit in `.github/build-watchdog.json` and opens (or updates) an issue `build-stuck`, which it closes when no build is stuck.
- **Firmware builds in GitHub Actions:** `.github/workflows/firmware-build.yml` (manual, owner only) builds the images in the pinned ESP-IDF container, writes `SHA256SUMS`, a build manifest and a provenance attestation, checks the version inside every image, opens an issue `build-failed` when it fails and prepares an unsigned draft release only after the owner approves it; the signature stays on the maintainer's computer. See `docs/BUILD.md`.
- **The machine page says how the machine changes the tools:** the model the server holds for the machine (`ccd-atc` is shown as `CCD ATC`) is written at the top of the page, and on the models with the tool changer (a word `ATC` in the name) the page says that the machine changes the tools by itself; the models with the manual change say nothing of the kind. At a tool change the page names the tool to put in (the number comes from the pause the server reports) and, on a changer model, says that the bar is not ready and the tool is changed by hand, because the server asks the operator only when the bar of the changer has not been measured.
- **A bar of the work in hand:** under the model the page shows the tool at work with its diameter and the holes (cuts) done of the ones it has, the next tool, the tools finished and the time left. It is worked out from the tools of the chosen file, taken in the order of their first hole or cut (the order the server works them in, not the order of their numbers), the tools switched off left out, the steps already done before a job that goes on left out, and the steps the server reports shared out over them (scaled when the server counts in another way, as it does for the paths of a routing file); the time left comes from the estimate of the server. The setting `tool_bar` (on by default) turns it off.
- **A summary of the plan before the start:** the job page and the confirmation of the start show the estimated time and, in the words of the operator, what the server found wrong in the work it planned: a work that is tiny or far from the corner, bigger than the table, a scale that is not 1, and a plan that goes past the course of an axis (with the axis).
- **The file is locked while the machine runs it:** a file chosen on the card while a job runs or waits at a tool change is refused with its reason, because it made the screen forget the job it was following; a job that is only ready, or that ended, can still be replaced.
- **Texts:** eleven new texts in the 37 languages (tools, time left, estimated time, the changer, the bar not ready, put in the tool, the four warnings of the plan and the locked file) and the fonts built again for the characters they need.
- **Tests:** `test_workflow` grows with the order of use of the tools, the steps shared out over them (switched off, resumed, scaled, finished), routing pens, the clock, the model with and without the changer, the fleet with the tool of a pause, the steps and the estimate, the lines of the page in several languages, the locked file, and the plan of the server with each of its warnings; `test_status` with the setting and the reason of the locked file; `test_locales` with the new keys. The firmware has not been rebuilt with this change.
- **Three checks that nothing ran are removed from `tools/`:** `_doc_policy.py`, `_readme_parity.py` and `_tracked_names.py` were copies of the checks of another family that no workflow, script or document named, and their header said another family kept them in step. The checks that run are in `tools/ci_validate.py`.
- **More host tests:** the languages and their fall-backs, the sound files that an operator puts on the card, the job that is running, the turn of the panel and the files of the card.
- **A sound file whose chunk ends past the end of the file is left alone** instead of moving the reader back onto itself on a 32-bit chip.
- **The workflows are hardened:** every action is pinned by its commit with its version in a comment, and the checkouts keep no credentials.

## [0.0.8] - Screens that tell the operator what happens

- **A missing key in any language fails the check:** `tools/test_make_locales.py` runs `make_locales.py --check` on the repository and on a copy with a key removed.
- **Robustness settings:** `sdkconfig.defaults` turns on the task watchdog (reset on a hang, both idle tasks watched), raises the stack of the main task above the default, and turns on the stack overflow canary and the FreeRTOS stack data. The firmware logs the stack each task has left (`HMI_STACK_REPORT_S`, `HMI_STACK_WARN_BYTES` in the menu) and warns when one is short. `tools/check_firmware_defaults.py` (with `tools/task_needs.py`) guards these settings and the stack of each task, and its tests run in the CI. Not built or run on a module; the stack numbers are to be tightened after a run on the board, and an old `sdkconfig` in a build folder must be deleted for the new defaults to apply.
- **The screen says what is wrong with `hmi.cfg`:** a line that cannot be used is shown under the top bar (the line, the key and why, in the language of the operator, with how many more there are) instead of being ignored in silence, and a missing file says so. The reason of every problem is now a code (`CfgReason`) next to its English text for the log.
- **The server is checked at the start:** no `server_host` or no answer on the port (`18200` by default), or an answer that is not from an EH3D server, shows a clear note with the address once, when the state changes.
- **The connection state is always visible:** the top bar says connected, no connection or other server (an answer that is not an EH3D fleet, or a server that does not list the machine of the settings), and the data are marked old, with their age, when the server has not updated them for `stale_after_s` seconds (new setting, 15 by default, 2 to 3600); the list of machines turns amber and each row says `Old data`.
- **The confirmation counts down and speaks the language of the operator:** the dialog shows the seconds left before it aborts by itself (`confirm_timeout_ms`) and names the order (`Stop the machine`, `Start the job`, `Jog X -`, `Spindle 12000 rpm`) in the 37 languages instead of the internal id.
- **No more English literals in the notes of the screen:** the notes of the application (stop sent or not sent, file chosen, nothing to send, going on from the holes done...), the reasons of the job workflow, the errors of the connection and the names of the orientations and of the spindle choice are texts in the 37 languages; 52 new texts in all, with the fonts built again for the characters they need.
- **The position bar no longer shows invented numbers:** it shows dashes until the position is read from the machine.
- **Version on the screen and name in every request:** the firmware version is on the title bar and in the settings, and every request to the server carries `name/version` in the headers `User-Agent` and `X-EH3D-Client` (`client_id`, `wire`).
- **Tests:** new `test_status` (the report of `hmi.cfg`, the link and the age of the data, the notes, the order and the countdown, the identification of the client), the keys and texts in `test_locales`, the age setting in `test_status`, and `tools/test_check_firmware_defaults.py`. The firmware has not been rebuilt with this change.
- **A self-test for the day the screen meets the hardware:** `tools/selftest.py` checks `hmi.cfg.example` (or `--cfg FILE`) with the rules of the firmware, starts a toy server on port 18200 and checks that its answers are what the screen's parsers need; with `--server HOST:PORT` it asks a real server the same questions with GET only. It writes `selftest_bungard-hmi_<time>.txt`, sends nothing to hardware and never prints the token. Its tests run in the CI.
- **`docs/HARDWARE_CHECKLIST.md`:** the steps to do by hand on the screen, with what must happen and where to write the result.
- **`hmi.cfg.example` is read by the screen:** the explanations moved to their own lines, because a comment after a value is part of the value and made the screen reject the line.

## [0.0.7] - Start, pause and stop that work, and warnings of the board and of the job

- **A board larger than the table is warned about:** choosing a drilling or routing file on the card compares the size of its box (the holes, or the moves of the pen) with the table of the machine - the course that the server reports less the offset, read from the configuration file of the machine, or `table_width_mm` and `table_depth_mm` of `hmi.cfg` when the server does not say it - and a board that fits neither lying nor turned is warned about on the job page with its size and by how much it goes over. The job is not blocked: the server refuses what lies outside the table.
- **A job that was cancelled or failed is not a finished job:** the screen says which of the two it was, with the reason of the server, never marks it as finished, plays no notice of the end for it and does not forget it before the server has said how it ended; it is kept to go on from the holes already done. A job that left the machine and whose end the server has not yet told is neither finished nor stopped.
- **The notes of the server about a job are shown:** what a job asks for beyond the spindle of the machine (turns or feed above or below what it holds) is listed on the job page when the job is made.
- **Texts:** one new text for the board that does not fit and one for a failed job, in the 37 languages, and the fonts built again for the characters they need.
- **Tests:** `test_workflow` grows with the box of drilling and routing files, the board that fits, fits turned and does not fit, the table from the configuration of the machine, the cancelled, failed and finished jobs, and the notes of the server; `test_hmi` with the two new settings.
- **The screen looks for the server on port 18200**, the port the server listens on, in the default and in `hmi.cfg.example` (it was 8080, so a configuration that only named the host never reached the server).
- **Starting a job works:** the start of a job that is ready no longer waits for an armed link (a job is armed only once it runs, so the start was always refused). It has its own kind in the gate: it still needs the stop released and the hardware stop wired when the setting asks for it, and it asks for the confirmation like a move; the question is no longer dropped while the link is not armed. With the bench setting that turns the question off, the order now goes at once instead of doing nothing, and a start with no job ready says so before asking anything.
- **Pause holds, it no longer cancels:** the pause button asks the server to hold the job (`POST /api/v1/jobs/:id/pause`) and a new button lets a held job go on (`/resume`); the pause is never held back by the gate. The server holds only G-code jobs, so for a drilling or routing job its reason is shown on the screen and the job keeps running.
- **Tool change:** while a job waits at a tool change, a new button ("tool changed") answers it through the gate and sends the confirmation to the server.
- **The stop goes first:** the stop has a task of its own, no longer a place in the queue behind other requests, with a short timeout and three tries; it cancels the job the fleet shows on the machine (also one started from another program or screen) and the own job when it is another one. If it could not be sent the screen says so. Pressing the hardware stop sends the same stop to the server, once for each press.
- **Texts:** one new word (tool changed) in the 37 languages and the fonts built again for the characters they need. The spoken order for a pause is now a pause, and the one for a start is a start.
- **Tests:** `test_hmi` grows with the start of a ready job through the gate (and its confirmation while the link is not armed), the pause that is never held back and the press of the hardware stop as an edge; `test_workflow` with the pause, the release of a held job, the tool change as the only thing `confirm` answers, and the requests of a stop (fleet job, own job, both, none). The firmware has not been rebuilt with this change.
- **The job flow is the same as in the other touch screen:** the flow of a job and the link to the server are now one code in both screens (kept identical by the shared firmware base), so the flow also takes a G-code program from the card and sends it as a G-code job; on a drilling machine the server refuses it with its reason, which the screen shows.

## [0.0.6] - Resume a stopped job through the server

- **Going on after a stop through the server:** EH3D-SERVER keeps the request of every job and makes the new one itself (`POST /api/v1/jobs/:id/resume-from`, with `skip` brought forward and the tools off kept), so the screen asks for that instead of sending the file again (`job_resume_from_request`, `Workflow::resume_request` and `on_resume_from`). A job that was stopped goes on even after a reset of the screen (it follows the job again and has no file) and without the file on the card. The new job is only made ready (`resumed_from` is shown on the job page), it waits for the operator, and the start goes through the gate as any other, with the spindle turns cut to the limit. A server that does not have the route (404 or 405, but not the 404 of an unknown job) is remembered as an old one and is answered as before with the file the screen keeps; a refusal of the server (`409 not_stopped`, `422 no_work`) is shown with its reason, and a second touch while the answer is awaited does not make a second job. A job followed again after a reset now also knows from the server whether it was a drilling or a routing job (holes or cuts).
- **Texts:** one new word in the 37 languages (resumed from) and the fonts built again for the characters they need.
- **Tests:** `test_workflow` grows with the new job made by the server (also after the second stop, after a reset and for a routing job), the 409, the 422, the 404 of an unknown job, the old server (404 and 405) with the fallback to the file, an old server with no file, an answer with no job, and the link that fails. The firmware has not been rebuilt with this change.

## [0.0.5] - Spindle limit of the server on the gate, resume after a stop and drilling then routing

- **The gate keeps to the spindle:** a spindle order carries the turns it asks for (the new setting `spindle_rpm`, 12000 by default, is what the spindle button asks), and the gate never lets it ask for more than the lower of `spindle_max_rpm` and the top speed of the spindle the machine carries, as the server says it. With the new setting `spindle_over = clip` (the default) an order for more is cut to that speed and the screen says so; with `refuse` it is refused with a reason. The confirmation of the spindle shows the turns it will really get ("spindle on 18000 rpm"), a move is never cut, and a stop is never held back. The settings page has a button that switches between cut and refuse until the next start.
- **A stopped job goes on:** when a job leaves the machine the screen asks the server how it ended; a job that was cancelled or failed is shown as stopped with the holes (cuts) it did, and a button sends the same file again with `skip` set to those already done, so only the rest is drilled (or routed). The tools switched off stay off, a second stop adds to the holes already done, and the start goes through the gate like any other. A job followed again after a reset has no file on the screen and cannot be resumed from it.
- **Drilling and then routing:** a drilling file and a routing file chosen one after the other are two programs of one job. The drilling goes first; when the server says it is done, the routing is made and waits for the operator to start it (after the change of tool), and the job page names the program that comes next. A drilling file with every tool off passes on to the routing file.
- **Texts:** five new words in the 37 languages (the order was cut to the top speed of the spindle, the refusal of an order beyond it, resume, stopped, next) and the fonts built again for the characters they need.
- **Tests:** `test_hmi` grows with the cut and the refusal of the spindle (the limit of the setting and of the machine, the confirmation, the voice, the bench setting without confirmation) and `test_workflow` with the report of a job, `skip`, the stop and resume (twice), the chain of the two programs and the passing over of a program with nothing to do. The firmware has not been rebuilt with this change.

## [0.0.4] - Tools of the file on the screen, the spindle of the server and 37 languages

- **The tools of the chosen file, and tools that can be switched off:** the job page reads the drilling file (Excellon: the tools declared, their diameter, inches turned into millimetres, and the holes of each) or the routing file (HP-GL: the pens and their cuts) when it is chosen, shows how many holes or cuts it has, and gives one chip for each tool (`core/job_tools.hpp`). A tap on a chip switches that tool off or on; the job is sent to EH3D-SERVER with `skip_tools` (the server leaves their holes or paths out and they need not be in the tool table), the file on the card is never changed, a new file starts with every tool on, and when every tool is off nothing is sent and the screen says so. The same chips are in the desktop program.
- **The spindle of the machine on the job page:** the screen asks the server for the spindle the machine carries (`original` or `vfd`) at the first reading and then every tenth, and shows it with its slowest and fastest turns; a job beyond what the spindle gives is refused by the server and the screen shows the reason. `spindle_ceiling` gives the most the screen may ask (the setting `spindle_max_rpm` and the spindle, whichever is lower).
- **Texts:** two new words (holes, cuts) in the 37 languages, and the fonts built again for the characters they need. The 29 added languages are translations that wait for a review by native speakers; Brazilian Portuguese and Canadian French take the word of European Portuguese and French of France.
- **Tests:** `test_workflow` grows with the reading of both kinds of file, the switching of tools, the `skip_tools` of the request, the refusal of a job with nothing left and the reading of the spindle. The firmware has not been rebuilt with this change.

- **Thirty-seven languages on the screen:** besides English, Spanish, Italian, German, French, European Portuguese, Chinese and Japanese, the texts of the screens (the tabs, the buttons, the refusals of the gate, the whole quality check and every finding of the analyser) are written in Bulgarian, Croatian, Czech, Danish, Dutch, Estonian, Finnish, Greek, Hungarian, Irish, Latvian, Lithuanian, Maltese, Polish, Romanian, Slovak, Slovenian, Swedish, Norwegian, Icelandic, Ukrainian, Russian, Serbian (Cyrillic), Albanian, Catalan, Galician, Basque, and the two variants Brazilian Portuguese and Canadian French (which hold only what changes). One file each in `locales/` (`Key<TAB>text`), compiled into `core/locales_gen.hpp` by `tools/make_locales.py`; a text a language lacks is shown in English (in European Portuguese / French of France for the variants), and the setting `language` (and the notices `voice:LANG:f|m`) accept all the codes. The spoken alerts and orders stay in the first eight languages.
- **Fonts for them:** `tools/make_fonts.py` builds `main/fonts/eh3d_font_16.c` and `eh3d_font_24.c` with only the characters the screen can draw (Latin and Latin Extended and Cyrillic from Montserrat, Greek from DejaVu Sans, Chinese and Japanese from Source Han Sans), under 100 KiB of flash for both sizes, and writes `core/font_ranges.hpp`; the symbols of LVGL stay in the built-in Montserrat as the fallback. They are compiled into the firmware and set as the font of the screen; this has not been built into a firmware nor seen on the real screen.
- **A selector of language in the settings:** a list that scrolls with the 37 names, each in its own language, and the one in use outlined; the choice is kept until the next start (`hmi.cfg` holds the lasting one).
- **Tests:** `test_locales` (every key has a text in every language, nothing is empty or too long for the screen, the name `hmi.cfg` and the dots stay, the script of each language is the right one, and every character of every text, of the names of the languages and of the keyboards is in the range of the generated fonts); `python -I tools/make_locales.py --check` runs in the CI.

## [0.0.3] - Quality check with the camera of the drill head and the ring of LEDs

- **The notices are said by the screen:** the settings `sound_finish`, `sound_tool_change` and the two new `sound_check_ok` and `sound_check_bad` (the visual check of the board is correct, is not correct) are now played: off, a beep that the screen makes, or a recorded voice (`voices/LANG/f|m/<name>.wav` on the card, 16 bits, mono), which plays the beep when the recording is not there or is not that format. They are said by a task of their own at the volume of the settings, when a check just made is correct or not correct (never the last one shown when the page opens), when a job ends and when the machine asks for a tool. The four can be edited on the screen like the other settings.
- **Tests:** the reading of a recording and of its refusals, the beeps and the volume, and the new settings (`test_notices`, 92 checks).

- **Quality check and the ring of LEDs:** a sixth page shows the verdict of the check of the work through the camera of the drill head (OK, NOT OK or cannot judge, as big as a sign), the holes that are right, the width of the milled channels and a line for each finding, in the eight languages. Everything goes through EH3D-SERVER, which judges the picture and holds the profile, and the page shows the last check of the machine when it opens.

## [0.0.2] - Following the job after a reset, keyboards for each setting and a firmware that builds

## [0.0.1] - The rules of the screen, the settings file, the spoken orders and the first screens

- **The gate:** every move and every spindle order, from a touch or from the voice, passes one place that runs it, asks for a confirmation on the screen with a time limit or refuses it with a reason; a stop always goes, the hardware stop is a latch that only an acknowledgement on the screen clears once the button is up, nothing moves while the link is not armed, and a spoken order always asks.
- **The settings file:** `hmi.cfg` holds every tuned value (language, brightness, the server, the safety switches, the voice); a value out of range or an unknown key is reported and the safe default stays. `hmi.cfg.example` lists every key.
- **Voice:** spoken alerts and a short fixed list of spoken orders in eight languages; the orders that only halt are understood inside a sentence, the ones that move or spin must be said whole.
- **Eight languages:** English, Spanish, Italian, German, French, European Portuguese, Chinese and Japanese in the screens, the alerts and the orders.
- **Firmware:** the ESP-IDF project for the ESP32-P4 module with the LVGL machine screen, the stop button, the confirmation window and the hardware-stop input (written; not built or run on a module yet).
- **Standing up or lying down:** the setting `orientation` (`auto`, `landscape`, `portrait`) turns the picture of the panel; lying down the job, the plan view and the jog pad sit in three columns, standing up they stack, and a touch lands where the screen is touched.
- **microSD card:** the drilling, routing, Gerber, DXF and ZIP files of the card are listed, a file is chosen and read, and reports are written; only plain file names are accepted.
- **One more client of the server:** the screen reads the fleet every `poll_s` seconds, sends the chosen file as a job that waits ready, starts it through the gate, follows its progress and its stops for a tool change in real time, and keeps the answer of the server on the card.
- **The look of the desktop program:** the Forge theme, cards with cut corners, chips in the top bar, the bar of the position with the round stop button, and a preview of the screens in the README drawn from the texts of the firmware.
- **Tests:** two host test programs with 743 checks.
