# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **The contract of the settings of the server is the current one:** `answer_needs_question` is now on by default there (an answer to a job names its question, as this program already sends it). No other change.

- **The summary of a drilling file supposes nothing about its numbers:** the screen reads them as the file declares them and, for what it leaves open, with the format chosen in `drill_format`. When neither says enough, or the choice cannot be what the file says, the holes and the tools are still counted but the size of the board is shown as not known, with no warning against the table, and a diameter with no unit is not shown. Before, coordinates without a point were taken as thousandths. Choosing the format reads a file not yet sent again and keeps the tools switched off. Host-tested only; not seen on a module.
- **The documents say what exists today:** the releases carry firmware images built in GitHub Actions that have not been flashed or run on a module, the client of EH3D-SERVER is written and tested on a computer, and the copy of the settings contract has 107 settings (19 through the security page, 88 by file).
- **Third-party notices:** `docs/THIRD_PARTY_NOTICES` holds the licences and copyright notices of ESP-IDF, of the third-party code inside it and of the components the firmware is built with, made by `tools/third_party_notices.py` from the build of every board. The CI fails when a declared dependency is not listed.

## [0.1.5] - Spindle, drill format and resume questions of the server - firmware not tested on hardware

- **The numbers of host checks in the README were measured again.**

- **A drilling file that does not declare its number format can be sent:** the new setting `drill_format` of `hmi.cfg` (`ask` by default) and a choice in the settings of the screen send `drill_format` with the job; nothing is chosen until a person does. A refusal of the server for the format says in the eight languages where to choose it. Checked by the host tests; not seen on a module.

- **Before the tool goes down into the work:** when a job that goes on after a stop waits with `pause.plunge`, the screen says that continuing takes the tool down, in the eight languages. Host-tested only; the screen itself has not been looked at on a board.
- **The copy of the settings contract has `grbl_spindle_stop_on_pause`** (off by default: a pause of a GRBL machine also stops the spindle and the coolant), with the label and help of the server in the eight languages. Not tried on a screen.
- **The second question before the spindle or the laser goes on:** when a job that goes on after a stop waits with `pause.power_on`, the screen says that continuing again switches the spindle or the laser on, in the eight languages. It needs a server with that question. Host-tested only.

- **Safety: Continue and "Tool changed" answer the question on the screen.** The screen sends back the identifier of what the job asked when the button was pressed (`pause.question`), so a server that asks something else by then refuses the answer (`409 question_changed`, with its text in the eight languages) instead of taking it as the answer to a question nobody has read; the buttons are drawn again as soon as the question changes. The copy of the settings contract has the new setting `answer_needs_question` of the server (106 settings). A server of an earlier version is answered as before. Checked by the host tests; not tried on a screen.

## [0.1.4] - The settings of the server and the new resume warning - firmware not tested on hardware

- **Safety: the screen says that the spindle is started when a job goes on.** While a job that goes on after a stop waits before its first move, the job page warns that letting it go moves the machine back to where it stopped and starts the spindle the program had on.
- **The reason of a resume the server does not do is shown:** a `422 bad_request` of `resume-from` shows the reason of the server on the screen, not only that something was wrong.
- **The copy of the settings contract follows the server:** 105 settings in 17 groups, with the settings of a stop and of going on, and millimetres and micrometres written as `mm` and `µm`; the fonts hold the characters of the new texts.
- **Japanese and Chinese are drawn everywhere:** the two fonts of the screen are built again with every character of every text of the screen (the settings of the server, the refusals of the server, the sentences of the speaker), so those pages no longer fall back to English; the characters of the languages that were removed are no longer in them. `tools/make_locales.py --check` now looks at every source that holds text and the host tests fail when a text of any of the eight languages cannot be drawn. The new fonts have not been seen on the module.
- **The refusal codes added by the server since the last release have their texts in the eight languages**.
- **The shared lessons check reads only what is part of the repository:** what git ignores, and folders such as `managed_components` that a firmware build downloads, are no longer analysed, so the local validation no longer fails over downloaded code.

## [0.1.2] - The settings of the server drawn from its contract and its light view of the values in force, a login for the touch screen and the newest refusal codes in eight languages

- **The settings of the server are shown with their values in force to a login that is not an administrator:** `core/settings_values.hpp` reads the light view (`GET /api/v1/settings/values`, any login: the `hmi` application of an operator included, a few kilobytes and never more than 16 KiB) and the page draws the values with the labels and warnings of the copy the screen carries, read only. An administrator still reads the full contract; one whose token cannot read it falls back to the light view. Until now these logins saw the copy with no value at all.
- **`ETag` and `304`:** the link sends the tag of the last answer in `If-None-Match` and keeps the page when the server answers `304` (a few bytes instead of a few kilobytes); the tag is forgotten when the login changes or a read fails, and a header that is not a tag (a quote inside, a space, more than 100 characters, a break of line) is never sent or kept. The sockets keep 16 KiB for this route and report an answer over it as too long.
- **The page says when its copy of the contract is out of date:** the generator writes the SHA-256 of the contract it was made from (`kContractCopyHash`) and the page compares it with the `contract_hash` that the server gives in the light view and in the full contract; when they differ it warns that texts and keys may be out of date. A hash that is not 64 lower-case hexadecimal characters says nothing.
- **A secret and a path of the computer are never shown:** a key the server marks secret, or whose value is the mark `***`, is Hidden whatever the server sent in its place and no value is kept; a key whose value the server keeps back (`hidden`) says so; a value the server cut ends with an ellipsis; a key the copy does not know is drawn read only even when its value is kept back.
- **An answer that cannot be trusted is not drawn:** a key that is not a name of lower-case letters, digits and underscores, an entry that is not an object, a value that is an object, a text or a list over the limits, more than 256 keys, a count that is not the number of keys, an answer cut short or nested too deep ends as the copy of the screen with the reason in the language of the operator.
- **New lines in `hmi.cfg`:** `settings_values` (on) and `settings_values_poll_s` (30, 5 to 3600), with their ranges in `hmi.cfg.example`, in the self-test and in the README tables.
- **Three more sentences of the page in the eight languages of the tables:** where the values come from, a key the server does not show and the contract that is not the copy; the other 29 languages show the English ones.
- **112805 more checks in `test_settings`:** the light answer as the server writes it, the page of the light view in the eight languages, the `ETag` and the `304` against a simulated server, the header of the answer, who reads what (administrator, operator, viewer, unknown role, a token without the scope, the setting off, no login, an older server), the answers that go wrong, hostile documents, the file lines, a seeded storm of roles and failures and a seeded bending of the answer.

- **The settings of the server are drawn from its contract:** `core/settings_contract.hpp` reads `GET /api/v1/settings/contract` (the 89 settings in 15 groups of EH3D-SERVER, each with its type, range, default, unit, whether it applies at once or after a restart, the route that writes it, the role it needs, its risk and its label, help and warning in eight languages) and `core/settings_page.hpp` turns it into the block "Server settings" of the settings page: the value in force of each setting, the ones that are not the default in amber, a switch as On or Off, a number with its unit, a secret as "Hidden" (it is never asked for or shown). The link reads the contract after the first reading of the fleet and then every `settings_poll_s` seconds.
- **A copy of the contract travels in the screen:** `core/settings_contract_gen.hpp`, written by `tools/gen_settings_contract.py` from `docs/settings-contract.json` of the server (texts in the order of the tables of the screen, a document of another schema, a missing text or a route other than `PUT /api/v1/auth/policy` for a policy key is refused). When the live contract cannot be read (the login is an operator, nobody answers, the answer is too long, the schema is newer, the answer is not a contract) the page shows the copy, read only and without values, and says why in the language of the operator. `--check` fails when the file is not the one the server gives.
- **What the screen does not know is read only:** a key the live contract has and the copy lacks is drawn from the live contract, a key with a value and no entry is a read-only line with its name, a type it has never heard of is a read-only line, a group the contract does not list goes last, and a schema of a newer version is not drawn at all (the copy is shown). The page counts the keys the copy does not have.
- **The screen changes no setting unless `hmi.cfg` says so:** a change needs the live contract, the route `PUT /api/v1/auth/policy` and no other, a login as an administrator (the login now keeps the role the server gave it; a screen that uses the static `token` never learns its role), `settings_write = on`, the key in `settings_write_keys` and no job running (`settings_block_running`). The 70 settings that are set in `server.cfg` are shown and never written; a secret is never shown, asked for or written.
- **A change is asked step by step:** the question is in the words of the setting, a risky one shows its warning and asks a second time, a value the server calls looser than recommended (`409 weak_confirm_required`) is asked about a third time and sent with `confirm_weak`, each question has its own time and gives up by itself, and a spoken order never starts a change. What is typed is checked against the contract before anything is sent (type, range, length, choices). The answer is read by code (saved, saved after a restart, refused with the text of the code in eight languages, nothing sent); an answer of 200 that is not the JSON of the server is not a saved change.
- **New lines in `hmi.cfg`:** `settings_contract` (on), `settings_poll_s` (600), `settings_write` (off), `settings_write_keys` (none) and `settings_block_running` (on), with their ranges in `hmi.cfg.example`, in the self-test and in the README tables of the eight languages; a line that cannot be used changes nothing.
- **Warnings where the server and `hmi.cfg` disagree:** the page warns when `rack_max_slots` of the server is below the highest place of `rack_places`, and the core has the sentence for a file larger than `max_body_mb`.
- **The sockets keep up to 1 MiB for the contract:** the answer is some 250 KB, over the 256 KiB kept for any other answer, which would have made the live contract unreadable.
- **The table of the refusals of the server is up to date:** `core/server_errors_gen.hpp` has 151 codes (143 before); three codes of the server (`bad_bgcode`, `bambu_lan_off`, `bgcode_unsupported`) still have no eight texts in the table of the phone app and are shown as their code.
- **Texts of the page in the eight languages of the tables:** `core/settings_text.hpp` (35 sentences, the same holes in every language, formal register in German, French and Portuguese); the other 29 languages show the English ones, and a Japanese or Chinese text is drawn only when its characters are in the fonts of the screen.
- **Tests:** a new host test program, `test_settings` (29279 checks, with a seeded storm of failures against a simulated server and 300 bent documents), covers the copy (89 settings in 15 groups, 19 through the policy and 70 in the file, every one with its texts and a control), the copy written as the server writes it and read back by the code of the live answer, the documents the screen does not understand, the control and the checks of each type, who may change what, the steps of a change, the answers by code and the texts; `tools/test_gen_settings_contract.py` tests the generator. The READMEs state the counts of the programs as they are measured.
- **Documentation:** `docs/SETTINGS_CONTRACT.md` says what the screen shows, which keys it may change and why none by default, the lines of `hmi.cfg` and what has not run; the file tree and its picture, the tables of the READMEs, the checklist of the hardware day (five new steps) and the notes on the profiles are brought up to date.
- **The host tests and the READMEs count what is there:** `test_session` (the login, the tries again and the refusals by code) was already built here but not counted; the READMEs now state twelve programs and the checks of each, including the keyboard and the other programs whose numbers had moved.

- **The shared part of the screen is brought up to the one of the generic screen:** the client of the server (login as the application `hmi` with `server_user` and `server_password`, renewal of the login, tries again with `server_timeout_s` and `server_retries`, the machines of the plugins of the server), the table of the refusals of the server in eight languages, the new settings and their keyboards and the tests of the session come from the firmware base, so the two screens say and do the same with the server. The new `test_session` (4132 checks) runs with the other host tests; the screens of this repository do not call the login yet.
- **This screen is described as the generic screen plus a profile:** `docs/ON_THE_GENERIC_SCREEN.md` says that EH3D-NODE-HMI-GUI is the screen that grows, which settings are the profile of this machine, which files are the same in both repositories and which parts (the panel that moves the machine by hand and the card under the progress bar) are still written only here. Nothing is removed.

## [0.1.1] - Newest improvements of the screen node of the drill

- **The stop of the screen no longer waits in the queue of the touches, and it is tried again:** the touch of the stop sets a flag that the task of the stop reads, so it cannot be lost when the queue of eight is full (a touch of anything else that does not fit now says so); when the server cannot be reached the note stays and the stop is tried again every `stop_retry_ms` (1 second) up to `stop_retries` (10) more times, both in `hmi.cfg`. The host tests cover the flag and the plan of the retries.
- **After a health check that found nobody, or something that is not an EH3D server, the link sends nothing with the token or a body:** only the health check and the stop (always tried) go out, so a job file, a start or the token do not reach whatever answers on the address.
- **A number of the server is brought into range before it becomes an integer:** `percent`, the counters of a job, the tool, the limits of the spindle, the clock and the other whole numbers read from the answers of the server go through `Json::int_in(key, lo, hi)`, so a value such as `1e99` or an infinite one gives the end of the range instead of an undefined conversion; a host test covers it.
- **The shared part of the touch screen follows the shared base:** the stop now goes to the machine first (`POST /machines/<id>/stop`) with the cancel of the job kept as a backup, and the health check no longer carries the token.
- **Simulation of the server for the screen:** add `tests/test_sim.cpp`, a program that runs the screen against a simulated EH3D-SERVER in memory (one machine, one job that stops when it is told to) that can be made to fail: no answer, a router page, a missing token, a 503, an answer cut short and a degraded server. The screen is driven with its own requests, its own reading of the answers and its own state of the link and the age of the data, with the clock as a number; a seeded storm of 300 failures checks that the state of the link is always the one of the cause and that the same seed gives the same run. 1824 checks. The manifest now says `evidence: simulator`. Nothing has run on the screen (the Guition 10.1" with the ESP32-P4 and the ESP32-C6) or against a real server.

- **The CI validation checks the workflows and the lessons of past CI failures against a baseline:** `tools/workflow_hygiene.py` and `tools/lessons_lint.py` (copies of the shared tools) run in the validation, and only findings that are not in `tools/workflow_hygiene_baseline.json` and `tools/lessons_lint_baseline.json` fail it, so what exists today stays as it is and a new one is caught. `python tools/workflow_hygiene.py --root . --detail` and `python tools/lessons_lint.py --repo .` list the findings.
- **The validation of the CI is the reusable one of the documentation hub:** the job `validate` calls `validate.yml` of EH3D-DOCS (pinned by commit) and what the repository checks besides it is in jobs of their own, with the check of the CHANGELOG.

## [0.1.0] - Shared core of both screens, rollback of a new image and server health check

- **The settings file is tested damaged:** `test_hmi` reads the settings file cut at every place and in 600 copies with bytes changed, inserted or cut (a fixed seed), and no value ever leaves its range. The counts of the host tests in the README are the ones of the CI.

- **A pull request must bring a line in the changelog when it changes the code:** `tools/changelog_pr_check.py` runs in the CI of every pull request (a label `no-changelog` skips it).

- **The two screens share one `core/`:** the settings (`hmi_config.hpp`, with the panel that moves the machine by hand and the kind of machine), the gate, the keyboard, the texts, the 37 languages (`locales/`), `machine.hpp` and the fonts with their code ranges are the same files in both, kept equal by the firmware base of EH3D-COMMON; what one screen does not use the other leaves alone. The fonts are built from the literals of both screens, in GitHub Actions, with `lv_font_conv` 1.5.3 and the fonts of LVGL 9.3.0 (`EH3D_EXTRA_LITERALS` in `tools/make_locales.py` names the other screen's file).
- **The screen says when the server answers but is not well:** the health check tells `degraded` and the note `ui.SrvDegraded` is shown, in the 37 languages.

- **The build in GitHub Actions lists the biggest stack frames:** with `EH3D_STACK_REPORT=1` (set only by that build) the compiler writes the stack use of every function and the build prints the twenty biggest of `main/` and `core/` in its summary, with a warning on any above 2048 bytes; the image does not change.

- **The orders of the screen are an enum:** every button sends an `Op` (`core/ops.hpp`: stop, start job, pause, resume job, tool changed, home, spindle on) in the action, and the application compares that and not the text of the order; the text stays as the id the confirmation shows and `op_of` reads it back, with a test through the whole table so that the two cannot drift.

- **A new image goes back when the screen does not run:** `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` is on and `main/image_confirm.hpp` confirms an image written by an update after 30 seconds of running, or sends it back to the previous one at once when the display does not start; an image flashed through the cable is not touched.
- **The first request to the server is its health check:** after a start or when the link was lost the screen asks `GET /api/v1/health` (open to anyone, no token goes with it) and tells "nobody answers" from "something answers that is not an EH3D server" (`classify_health` in `core/server_link.hpp`) before it asks for the fleet.
- **The host tests also run under AddressSanitizer and UBSan in the CI:** the same programs are built with `-fsanitize=address,undefined` and run (an undefined behaviour stops the test), and `test.sh` / `test.bat` run the same steps as the CI (the repository checks, the tests of the tools, the pictures and the languages, and the host tests).

## [0.0.9] - The touch screen follows the changer chaining, the positions of the tools, the jog panel and the stage notices of the job

- **The card of the work in hand:** under the lines of the machine page, four blocks as in the desktop program: the tool and its step (number, diameter, place in the bar, hole or cut X of N), the times (left, elapsed and the local hour the job is expected to end at), the position and the depth (X, Y, Z, the stroke, the feed and the turns of the spindle) and the counters (holes done or length routed, tool changes). What the server does not report is a dash, never an invented number; the hour comes from the system clock, or from `time_s` of the fleet, and `clock_utc_offset_min`.
- **The end of the drilling is a stage, not the end of the job:** when a drilling program ends and a routing program comes next, the screen plays its own notice (`stage.wav` of the voice chosen with `sound_stage`, or a tone) and shows a window saying that the routing comes next, with the buttons to follow it or to stop (switch `stage_window`). The sound of the end and the order to take the board out now wait until the server says the whole job was done; before, the end of the drilling played the sound of the end of the job.
- **A panel to move the machine by hand:** a cross for X and Y, Z, steps of 0.01, 0.1, 1, 10 and 50 mm, a continuous mode in which a held arrow goes in stretches, three speeds and four places kept. Nothing moves while a job runs (`jog_block_running`) or the hardware stop is on, the head stays inside the table (`jog_limits`) and goes up to the clearance over the board before it crosses it (`jog_safe_z`). The steps, the speeds, the clearance and the depth of the board are in `hmi.cfg`. A move by hand does not need a running job to be armed, and the gate refuses it with its own reason while one runs. The moves wait for the link to the node: until it exists the screen says that nothing was sent and keeps its position.
- **The bar of the tool changer:** on a machine whose model says ATC the job page shows a square per tool with its place and its state, and a window "Positions in the bar" with a drop-down list of places for every tool. A tool without a place, a place the machine does not define (`rack_places`) or two tools in one place stop the start and the screen says which tool and why (switch `rack_check`). The places are given in order, the small drills first and then the cutters, until the operator changes them.
- **Drilling and routing chained in one tool change:** the request of the job carries `request_version` 2 and a `rack` with `first`, `carry_in`, `carry_out`, `slots` and `carry_slot` (switch `rack_chain`); the drilling leaves its last tool in the chuck and the routing takes it over. A server that answers 400 or 422 gets the job again without the bar, and one that does not say `rack_applied` is believed: the screen shows in red that the tool changes were not chained and does not send the next program as a chained one. See `docs/SERVER_CONTRACT_NEEDS.md`.
- **The fleet is read more fully:** `time_s` of the answer and, for the running job, `position`, `feed`, `spindle_rpm`, `depth_mm`, `tool_changes`, `elapsed_s`, `routed_mm` and `tool_slot`, all optional.
- **Texts:** sixteen new texts in the 37 languages (the card, the stages, the panel by hand, the bar of the tool changer and the reason for a move refused while a job runs) and the fonts built again for the characters they need.
- **Settings:** `jog_steps`, `jog_step`, `jog_continuous`, `jog_speed_slow`, `jog_speed_medium`, `jog_speed_fast`, `jog_speed`, `jog_chunk_mm`, `jog_clearance_mm`, `jog_board_z_mm`, `jog_below_board_mm`, `jog_block_running`, `jog_limits`, `jog_safe_z`, `rack_places`, `rack_check`, `rack_chain`, `stage_window`, `clock_utc_offset_min` and `sound_stage`, with their keyboards in the list of the settings that the screen edits and their rules in `tools/selftest.py`. Every safety switch starts in its conservative position.
- **What the screen shares with the desktop program is written down:** `docs/PARITY_BUNGARD_GUI.md` lists each function, whether it is done, missing, not applicable or done in another way, and why.
- **Tests:** a ninth program, `test_parity` (227 checks), on the places of the bar and their validation, the chaining of the drilling and the routing and the request of the second version, the workflow on a machine with the tool changer (the retry without the bar, the reply of the server), the card of the work and its hour, the stages, the panel by hand (steps, limits, safe height, hold, places, blocks) and the new settings; `test_locales` follows the new keys.
- **Brand:** Add the application icon and the logos of the program.
- **Shared checks updated:** the validator also compares the badge and the Version row of the README with the manifest, fails when one of its checks cannot run, and the CHANGELOG step of the workflow reads the base branch from the environment.
- **A watchdog for the manual build:** `.github/workflows/build-watchdog.yml` looks every hour for a build that stays queued or running longer than the limit in `.github/build-watchdog.json` and opens (or updates) an issue `build-stuck`, which it closes when no build is stuck.
- **Firmware builds in GitHub Actions:** `.github/workflows/firmware-build.yml` (manual, owner only) builds the images in the pinned ESP-IDF container, writes `SHA256SUMS`, a build manifest and a provenance attestation, checks the version inside every image, opens an issue `build-failed` when it fails and prepares an unsigned draft release only after the owner approves it; the signature stays on the maintainer's computer. See `docs/BUILD.md`.
- **The machine page says how the machine changes the tools:** the model the server holds for the machine (`ccd-atc` is shown as `CCD ATC`) is written at the top of the page, and on the models with the tool changer (a word `ATC` in the name) the page says that the machine changes the tools by itself; the models with the manual change say nothing of the kind. At a tool change the page names the tool to put in (the number comes from the pause the server reports) and, on a changer model, says that the bar is not ready and the tool is changed by hand, because the server asks the operator only when the bar of the changer has not been measured.
- **A bar of the work in hand:** under the model the page shows the tool at work with its diameter and the holes (cuts) done of the ones it has, the next tool, the tools finished and the time left. It is worked out from the tools of the chosen file, taken in the order of their first hole or cut (the order the server works them in, not the order of their numbers), the tools switched off left out, the steps already done before a job that goes on left out, and the steps the server reports shared out over them (scaled when the server counts in another way, as it does for the paths of a routing file); the time left comes from the estimate of the server. The setting `tool_bar` (on by default) turns it off.
- **A summary of the plan before the start:** the job page and the confirmation of the start show the estimated time and, in the words of the operator, what the server found wrong in the work it planned: a work that is tiny or far from the corner, bigger than the table, a scale that is not 1, and a plan that goes past the course of an axis (with the axis).
- **The file is locked while the machine runs it:** a file chosen on the card while a job runs or waits at a tool change is refused with its reason, because it made the screen forget the job it was following; a job that is only ready, or that ended, can still be replaced.
- **Texts:** eleven new texts in the 37 languages (tools, time left, estimated time, the changer, the bar not ready, put in the tool, the four warnings of the plan and the locked file) and the fonts built again for the characters they need.

## [0.0.7] - Start, pause and stop that work, and warnings of the board and of the job

- **The notes of the server about a job are shown:** what a job asks for beyond the spindle of the machine (turns or feed above or below what it holds) is listed on the job page when the job is made.
